# デスクトップ化と動画書き出しの調査（2026-09-14）

この文書は**調査と判断基準**であり、実測の報告ではない。作成環境はLinuxコンテナで、**Windows実機での計測は一切行っていない**。表中の「測る」項目は、Windows機を用意した担当者が埋めること。数値のない欄を埋めないまま採用を決めない。

## 1. 何のためにデスクトップ化するのか

ブラウザ版で足りているもの：描画、Panel操作、Timeline、Camera、音の配置と同期再生、紙コンテ出力、ブラウザ内への自動保存と復旧。

ブラウザ版で足りないもの（デスクトップ化の理由になるもの）：

| 不足 | 現状 | デスクトップで期待すること |
|---|---|---|
| ファイルへの直接上書き | 保存はダウンロード。同じファイルへ上書きできない | 通常のファイル保存・自動保存・バックアップ世代 |
| 素材の同梱 | `.contp`に画像/音声を含めない（IDのみ） | プロジェクトフォルダまたは単一ファイルに素材を含める |
| ペン入力 | Pointer Eventsの筆圧のみ。傾き・遅延は環境依存 | Windows Ink/ワコムでの筆圧・傾き・低遅延 |
| 動画書き出し | 実時間のWebM録画に限られる | 実時間より速いオフライン書き出し、H.264/ProResなどの選択 |
| 大規模プロジェクト | 保存はUIスレッドで直列 | ワーカー/別プロセスでの保存と書き出し |

デスクトップ化は目的ではなく、上の不足を埋める手段。埋まらないなら採用しない。

## 2. シェル候補と比較基準

**先に特定のフレームワークを前提にしない。** 下の項目をWindows実機で測ってから決める。

| 観点 | Electron | Tauri (WebView2) | .NET + WebView2 | 完全ネイティブ再実装 |
|---|---|---|---|---|
| 描画エンジン | 同梱Chromium（挙動が固定できる） | OSのWebView2（Edge更新の影響を受ける） | 同上 | 自前 |
| 配布サイズの目安 | 100MB超 | 10MB未満（WebView2ランタイム前提） | 数MB〜（.NETランタイム次第） | 実装次第 |
| 既存コードの再利用 | そのまま動く見込み | ほぼそのまま（file/IPCは書き直し） | 同左 | ほぼ作り直し |
| ペン入力 | Chromiumの実装に依存 | WebView2の実装に依存 | 同左 | 最も自由 |
| 音声 | Web Audio | Web Audio（WebView2） | 同左 | WASAPI等 |
| ファイル上書き | Node API | Rust側API | .NET API | 直接 |
| 追加言語 | 不要（JS） | Rust | C# | 要検討 |
| ライセンス | MIT | MIT/Apache-2.0 | MIT（.NET）/WebView2は再配布条件を要確認 | — |

### Windowsで必ず測る項目

1. **ペン入力**：筆圧の段階数、傾きの有無、ペンダウンから描画までの遅延（高速ストロークの追従）、パームリジェクション。
2. **ファイル上書き**：同名保存、書き込み中の電源断からの復旧、OneDrive等の同期フォルダ上での挙動。
3. **音声**：再生開始の遅延、長時間再生のずれ（本リポジトリのブラウザ実測は4秒で−2フレーム）、他アプリとの排他。
4. **メモリ**：500 Panel＋実画像/音声を開いた状態の常駐量と、3分書き出し中の最大値。
5. **起動時間**：通常権限のユーザーでのインストールと初回起動。
6. **更新**：Edge WebView2の自動更新でUIが壊れないか（WebView2採用時の固有リスク）。

判断の目安：**ペン入力と音声が実用に耐えるならWebView2系（配布が軽い）**、耐えないなら**Electron（描画エンジンを固定できる）**、どちらも駄目なら描画部分だけネイティブ化を検討する。この順で試す理由は、既存コードの再利用量が多い順だから。

## 3. 動画書き出しの選択肢

現在の実装（`src/animatic.js`）はブラウザの`MediaRecorder`を使い、**実時間で**WebM（VP9/VP8＋Opus）を録る。3分のコンテには3分かかる。フレームを正確に取りたい場合のために、PNG連番をZIPで出す経路も用意した（音は含まない）。

| 方式 | コーデック/形式 | ライセンス・再配布 | 速度 | 備考 |
|---|---|---|---|---|
| MediaRecorder（実装済み） | VP8/VP9＋Opus（WebM） | ロイヤリティフリー。追加ライブラリなし | 実時間のみ | 対応は環境依存（`MediaRecorder.isTypeSupported`で確認して表示） |
| WebCodecs＋自前mux | VP9/AV1＋Opus | 同上。muxerライブラリを足すなら要確認 | 実時間より速い | 対応ブラウザが限られる。次の候補 |
| ffmpeg（外部プロセス） | H.264/ProRes/その他 | **LGPL/GPLの選択とH.264の特許プールに注意**。同梱するなら配布条件を必ず確認 | 速い | デスクトップ化とセットで検討する |
| ffmpeg.wasm | 同上 | 同上＋wasmの容量（数十MB） | 遅い | ブラウザ単体で完結するが容量と速度が不利 |
| PNG連番＋外部エンコーダ（実装済み） | 任意 | アプリ側に追加なし | フレーム厳密 | 現状の推奨。ZIPを解いて好きなエンコーダへ渡す |

**H.264を既定にしない理由**：特許プール（MPEG LA/Via LA）の扱いが配布形態によって変わるため、ロイヤリティフリーのVP9/Opusを既定にし、H.264は外部エンコーダ利用時の選択肢として扱う。

**追加ライブラリを入れるときの確認項目**（この方針は依存を足す全ての場面で同じ）：ライセンス、再配布条件、保守状況（直近のリリース）、配布サイズへの影響、性能への影響。現時点でアプリは実行時の外部依存ゼロを維持している。

## 4. 次の担当者への手順

1. Windows機でセクション2の6項目を測り、この文書の表を数値で埋める。
2. ペン入力と音声の結果でシェルを決め、理由と数値を同じ文書に残す。
3. 決めたシェルで、ファイル直接保存・素材同梱・クラッシュ復旧を先に作る（現行の`ProjectRepository`の役割をそのまま置き換える）。
4. 書き出しは、実時間録画から**オフライン書き出し**へ移す。映像は`animatic.evaluate`／`renderFrame`、音は`audio.scheduleFor`をそのまま使い、フレーム評価を二重に持たない。
5. 3分・音付きの書き出しを実機で計測し、[DEVELOPMENT.md](DEVELOPMENT.md)へ記録する。
